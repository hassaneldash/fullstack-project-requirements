Part 1

The Scenario

1 The Problem Story Context

Before writing a single endpoint or designing tables, you must understand that backend systems do not exist to render beautiful buttons—they exist to govern data pipelines, protect integrity rules, and expose secure communication endpoints. For this project, you are building the backend core for an Academic Mentorship & Code Review Platform.

The system's ecosystem relies heavily on specialized Stacks (Tech Categories). These represent distinct learning domains (like "React Engineering", "Python Systems", or "System Design"). Every Stack must be tracked with a unique identity name and a technical summary description outlining its competency benchmarks.

Under these Stacks work our technical experts, the Mentors. For every Mentor, the platform must capture their full name, bio details, and professional verification status. A Mentor is assigned to align with exactly one primary technical Stack, but a single Stack naturally houses many matching Mentors.

The platform services junior developers, our Students. To manage enrollment vectors safely, the system explicitly logs each Student's full registration name, date of profile creation, and contact parameter flags.

The absolute core transaction of the architecture is managing Review Sessions. When a student requests a consultation or portfolio audit, a Review Session record is generated. Each Session explicitly logs the targeted date and time, the student's submission description (e.g., "Reviewing an asynchronous race condition in my Node engine"), and the current operational booking status ('Scheduled', 'Completed', or 'Canceled'). A Review Session is strictly linked to exactly one Mentor and exactly one Student.

The Real-World System Bottleneck

Because peer evaluations are time-sensitive, the platform requires automated auditing. When a student schedules a Review Session, the backend must pass that text submission description directly to a code classification pipeline. The evaluation engine returns a Session Audit Log containing an auto-generated technical tag and a prediction confidence metric. This log must be safely preserved and linked directly back to the session, allowing mentors to review structural notes before the meeting kicks off.

🏗️ Structural Constraints (Data Integrity Expectations)

  • The data persistence tier must run strictly via relational SQL rules to completely eliminate orphan records or missing audit history.
  • Data integrity rules (Foreign Keys and Cascade protections) must be strictly implemented at the table constraints tier.
  • Concurrency Verification Block: Bookings must run through a transaction with strict isolation logic. The engine must reject bookings where the requested start time is less than an existing session's end time, and the requested end time is greater than an existing session's start time for that mentor.
  • The architecture must enforce transactional atomicity: if the Session Audit Log fails to instantiate, the Review Session must rollback cleanly to prevent data inconsistencies.

Part 3

Database Architecture

3 Entities, Columns & Data Types Data Layer

Regardless of the backend framework you choose, your tables must strictly mirror this relational column specification layout:

Entity (Table) Attributes (Columns) Description / Integrity Rule
User id [PK], email (Unique), password_hash, role (Admin/Mentor/Student), created_at Central identity store. Handles unified JWT authentication and strict Role-Based Access Control routing.
Stack id [PK], name (Unique), description Technical domains (e.g., Python Systems, React Engineering).
MentorProfile id [PK], user_id (FK/Unique), stack_id (FK), name, title, bio, is_verified (bool), average_rating (float), hourly_rate (decimal) The expert profile tied 1:1 to a User. Includes custom professional titles, admin verification toggles, and sorting metrics requested by the frontend.
MentorAvailability id [PK], mentor_id (FK), day_of_week, start_time, end_time Weekly operating windows. Interrogated by the client using targeted date parameters to dynamically compute available, unbooked 45-minute blocks.
StudentProfile id [PK], user_id (FK/Unique), name The junior developer profile tied 1:1 to a User.
ReviewSession id [PK], mentor_id (FK), student_id (FK), start_time, end_time, description, status (Scheduled/Completed/Canceled) The central transaction. Evaluated under isolation rules to mathematically prevent timeline overlaps during concurrent bookings.
SessionAuditLog id [PK], session_id (FK/Unique), predicted_tag, confidence_score (float), status (SUCCESS/FAILED), error_message, latency_ms Preserves a log of external execution telemetry metadata.

* Note: [PK] represents Primary Key (Unique row identifier) and [FK] represents Foreign Key (Structural pointer to a parent record).

Part 4

Cardinality & Participation Mapping

4 Entity Connectivity Mapping ERD Logic

Before coding your entities, evaluate these structural data linkages:

  • Stack to Mentor (1:N): One Stack houses many Mentors. A Mentor must belong to exactly one primary technical category. Participation is Total on the Mentor side.
  • Mentor to ReviewSession (1:N): One Mentor hosts many Review Sessions. A Session must have an assigned Mentor. Participation is Total on the Session side.
  • Student to ReviewSession (1:N): One Student requests many Review Sessions over their lifetime. Participation is Total on the Session side.
  • ReviewSession to SessionAuditLog (1:1 Case B): One Review Session is processed to map exactly one Session Audit Log. Participation is Partial on the Session side (if a session has just been logged but not processed yet) and Total on the Audit Log side.
Architectural Insight for AI Engineers: Notice that while Students and Mentors share a theoretical Many-to-Many connectivity matrix, it is completely resolved at the data tier using the ReviewSession entity as a Resolution / Junction Table.
Part 5

Framework Execution Blueprints

5 Selectable Tech Infrastructure Ecosystem Choice

Your team has the explicit freedom to choose **one** of the following five core backend stacks. Each blueprint below dictates how your file management framework must look to ensure grading equity:

Option A: Django REST Framework (Python)

Best for built-in administrative engines and rapid ORM scaffolding via clear Model definitions.

  • Use uv to spin up environment files, installing django, djangorestframework, djangorestframework-simplejwt, and pillow.
  • Isolate logic by separating features into an app folder (e.g., mentorship/).
  • Expose API serialization structures via a explicit serializers.py mapping file.

Option B: FastAPI (Python)

Best for high-performance async processing blocks and native Pydantic validation boundaries.

  • Build an enterprise directory pattern utilizing routers/, models/, and schemas/ folders.
  • Utilize SQLAlchemy or SQLModel to map data relations asynchronously.
  • Enforce dependency injection tokens to evaluate user authentication parameters gracefully.

Option C: Laravel (PHP)

Best for elegant ActiveRecord mapping syntax (Eloquent) and integrated robust routing blocks.

  • Initialize structural migrations folders using standard artisan CLI commands.
  • Isolate business logic blocks safely within specialized Controllers/ and Requests/ tiers.
  • Utilize Laravel Sanctum or Passport to enforce bulletproof JWT session evaluation rules.

Option D: NestJS (TypeScript)

Best for highly typed, scalable architectural patterns mirroring standard Angular design strategies.

  • Create independent modules using the standard nesting structure (e.g., mentor.module.ts).
  • Leverage TypeORM or Prisma to design structural Data Mapper schemas securely.
  • Protect routes by establishing Guard controllers executing JWT Passport validation mechanisms.

Option E: Express.js (JavaScript / Node)

Best for completely unopinionated lightweight freedom, demanding explicit manual folder architecture setup.

  • You must build a highly modular directory pattern manually, creating controllers/, routes/, and models/.
  • Utilize Sequelize or Mongoose/Prisma to govern data-layer validation interfaces.
  • Enforce authentication checking via independent, custom middleware middleware functions.
Part 6

API Protection & Integration

6 Guarding the Gateway Security

Because open endpoints invite denial-of-service spam risks, you must protect your infrastructure across three core levels:

  1. Environment Variables Encapsulation: All database passwords and external AI authorization tokens must live inside a root-level .env file. Under no circumstances should secrets be hardcoded into project setting files. Ensure .env is added to .gitignore.
  2. JWT Token Evaluation: Restrict booking and modification access points. The client must present a valid Bearer <token> authorization header before access is granted.
  3. Robust Telemetry Tracking: Implement secure exception blocks wrapping all external model executions. Network requests will fail; if an outage occurs, intercept the error payload, log the error_message directly to your table row, and preserve service uptime.
Submission Rule: All chosen project backends must provide a comprehensive, functional collection mapping (Postman or Insomnia JSON collection file). The file must verify clean request/response data shapes across all endpoints listed in the companion React frontend specification.
